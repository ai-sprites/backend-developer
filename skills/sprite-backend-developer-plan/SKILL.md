# PLAN — 明确实施依据

**输入：**当前请求与已确认验收、项目代码和测试、适用设计/架构/ADR 与真实契约。

**输出：**可以直接实施的范围、最小完整调用链、变更顺序和检查安排；需要持久依据时保存 `docs/backend-developer/<feature-id>/implementation-plan.md`，有排序或分工价值时再建任务表。

## 1. 读来源，确认适用范围

读取请求、项目约定、README、相关实现与测试、已确认需求和设计、已接受 ADR、架构及契约，记录真实路径与版本。沿用已指定资料仓库、部署单元和固定版本，不把观察或建议当成已确认约束，也不要求其他角色或固定格式材料齐全。

按 [工作方法的职责与授权边界](../sprite-backend-developer-services/references/workflow.md#职责与授权边界)核对当前任务。普通框架、库、工具与依赖选择在已授权开发范围内自行处理，兼顾需求、维护和兼容并简述理由。重要架构、共享契约、兼容承诺、昂贵或难逆迁移及风险接受沿用已有决定；仍缺人的决定时说明具体影响，只暂停依赖部分，答案写回来源和决定人。

## 2. 沿调用链找最小完整改动

从业务动作定位入口、领域规则、持久化与外部副作用，列受影响路径、消费者及必须保留的旧行为。保持满足需求的既有模块、协议和接口风格，拆服务必须有当前所有权、部署、规模或隔离需要，避免重复权威数据与无依据通用框架。

涉及输入、身份或资源权限时读 [边界与授权](../sprite-backend-developer-services/references/boundaries-auth.md)，明确可信校验位置、主体、资源归属及租户边界。已确认 HTTP 状态、响应结构、分页与权威契约是约束；项目采用 OpenAPI YAML 时标出主源和需同改同查的提供方、消费者。

## 3. 安排数据、失败与协作顺序

明确数据所有者、不变量、事务边界、并发、重复、超时、取消、失败及运行信号。涉及外部调用或任务时读 [集成与恢复](../sprite-backend-developer-services/references/integrations.md)；需要深化查询、一致性或已授权迁移时使用可选 `sprite-backend-developer-data` 数据专项。

涉及接口或数据变化时写清旧消费者、旧数据、部署兼容窗口及迁移/恢复验证安排，区分编写代码、环境演练和真实数据执行的授权。多人协作在共享契约、公共库、工作区或根配置、CI、公共测试编辑前确定单一编辑者与交接顺序，让所有参与者读取同一分工；独立文件可并行，不额外要求总负责人。

## 4. 将改动与检查对应起来

为变化结果、重要旧行为及相关授权、失败、一致性、兼容路径选择项目现有或已核实的检查。写清每项预期检查什么、依赖何种环境或数据、哪些项暂时受阻；不为无行为变化凑镜像测试。

需要持久依据时按 [模板与交付](../sprite-backend-developer-services/references/delivery.md)读取完整实施计划和适用任务模板，再写目标、范围、受影响路径、保留行为、顺序、验收与真实风险决定。普通小改动直接保留清楚的实施依据，不强制创建三份文档。已有计划局部更新，说明哪些旧结论仍适用或已替代，未验证旧结果不当当前证据。

## 完成条件与下一阶段

- 来源与版本、范围、适用决定和重要未决项清楚。
- 实施者能从依据找到完整调用链、改动顺序、共享分工和保留行为。
- 验收与具体检查对应，受阻只限制依赖工作；按需产物已保存到业务仓库并有真实链接。

完整开发任务继续 [IMPLEMENT](../sprite-backend-developer-implement/SKILL.md)。用户只要计划时交付计划、决定缺口和下一步，在此结束。
